# F5: Game industry tricks for real-time particle water

## Findings

### [1] Falling sand games use grid-based cellular automata with per-particle update functions, not physics-based particle systems
- quote: "The state for a single particle is represented as a 32 bit struct... species, ra, rb, clock. The first field, species, is a custom enum type... ra and rb are two 8 bit 'registers' for storing extra cell state beyond species... clock is just used to prevent a single particle from being simulated multiple times in a single tick"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [2] Noita's Falling Everything Engine simulates every pixel as a material with simplified physics reactions
- quote: "every pixel in Noita is made of some material. The different materials are simulated. E.g. Water will behave like a liquid, gasses will rise, sand will pile up, rigid bodies will rigid body... In addition to that we run simplified simulations of various chemical reactions, electricity, thermodynamics and so on."
- url: https://noitagame.com
- source_type: primary
- published: unknown (game released 2020)
- confidence: high

### [3] The key architectural pattern is a dense 2D array where particle position is implicit in array index, eliminating per-particle x,y storage
- quote: "as opposed to a particle simulation where we maintain a list of entities and their positions, here we store all particles in a dense 2D array, and directly encode the position of a cell as its location in that grid"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [4] Water simulation in falling sand games uses simple local rules: try to fall down, then diagonal, then spread horizontally with direction bias
- quote: "pub fn update_water(cell: Cell, mut api: SandApi) { let mut dx = api.rand_dir(); let below = api.get(0, 1); if below.species == Species::Empty { api.set(0, 0, below); api.set(0, 1, cell); return; } else if dx1.species == Species::Empty { api.set(0, 0, dx1); api.set(dx, 1, cell); return; }... let left = cell.ra % 2 == 0; dx = if left { 1 } else { -1 };"
- url: https://github.com/MaxBittker/sandspiel/blob/master/crate/src/species.rs
- source_type: primary
- published: 2019 (GitHub repo)
- confidence: high

### [5] Swap-based movement is the universal pattern: write EMPTY_CELL to old position, write particle to new position
- quote: "if neighbor.species == Species::Empty { api.set(0, 0, EMPTY_CELL); api.set(0, 1, cell); } else if api.get(dx, 1).species == Species::Empty { api.set(0, 0, EMPTY_CELL); api.set(dx, 1, cell); }"
- url: https://github.com/MaxBittker/sandspiel/blob/master/crate/src/species.rs
- source_type: primary
- published: 2019 (GitHub repo)
- confidence: high

### [6] Sandspiel separates particle simulation (CPU/WASM) from fluid/wind simulation (GPU/WebGL Navier-Stokes) for performance
- quote: "The main simulation, controlling the movement and interactions of all of the elements, takes place in Rust in a class called Universe... Sandspiel's fluid simulation usually really stands out... it's largely ripped from Pavel Dobryakov's WebGL Navier-Stokes implementation"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [7] A 32-bit cell struct enables zero-copy rendering by treating game state buffer as a texture directly
- quote: "Because our game state data is arranged in such a way that it happens to be a valid image texture, we can ship the whole grid over to the GPU with minimal copying and allocation! This was a big deal for making Sandspiel's rendering performant- the rendering code blocks the CPU for less than 1 millisecond"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [8] Minecraft water uses a fundamentally different approach: block-state propagation with flow levels rather than particle physics
- quote: "Water spreads at a rate of 1 block every 5 game ticks, or 4 blocks per second... When spreading horizontally, a weight is assigned to every direction water can flow. For each direction, this weight is initially set to 1000. Then, for every adjacent block it can flow into it tries to find a way down that is reachable in four or fewer blocks"
- url: https://minecraft.wiki/w/Water
- source_type: secondary
- published: 2026 (wiki, continuously updated)
- confidence: high

### [9] Sandspiel achieves 60fps on a 300x300 grid (90,000 cells) in Rust/WASM, even with suboptimal compiler settings
- quote: "A big mistake I made was to immediately take this extra performance budget and 'spend it' to increase my canvas size from 250x250 to 300x300, because now I could still get 60 fps on the 300x300 canvas. This was a blunder because there are a ton of devices which can't run sandspiel at 60fps"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [10] DAN-BALL Powder Game (the genre originator since 2006) supports 30+ element types including water, gas, wind, and pressure simulation
- quote: "Simulation game that reproduces such phenomenon with powder (dot)!" with elements including "[WATER] Water splash", "[GAS] Flammable gas", "[AIR] Left click increases pressure while right click decreases it", "[CLOUD] Rain cloud, snow cloud, and thunder cloud"
- url: https://dan-ball.jp/en/javagame/dust/
- source_type: primary
- published: 2006 (game), fetched 2026
- confidence: high

### [11] The update-scan order (top-to-bottom, left-to-right) combined with a clock bit prevents particles from "teleporting" multiple cells per frame
- quote: "clock is just used to prevent a single particle from being simulated multiple times in a single tick if it moves in the same direction as the update scans. Because we execute cell update functions one at a time from left to right and top to bottom, if a particle something is moving down, it will keep bumping itself ahead of the 'scan line' and could move many spaces in a single frame"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [12] bevy_falling_sand (Rust) uses velocity-based simulation with chunk-based updates — only chunks with active particles are simulated
- quote: "A velocity-based falling sand simulation built with Rust and Bevy!... Currently, the simulation is chunk-based, meaning that only chunks who have updating particles are simulated."
- url: https://github.com/100-TomatoJuice/bevy_falling_sand
- source_type: community
- published: 2023 (GitHub repo)
- confidence: high

## Suggested follow-ups
- What is the optimal grid size for 500 water particles on a TUI canvas (e.g., 120x40 = 4,800 cells)? Sandspiel achieves 60fps at 90,000 cells, so 4,800 cells is trivially fast.
- Should water particles be simulated as individual tracked entities (100-500 particles with positions) or as cell-automata in a grid? For "trapping rain water" visualization, tracked particles falling into terrain valleys may be simpler than full cellular automata.
- Can the Sandspiel water update pattern (fall→diagonal→horizontal spread with direction bias) be simplified to just (fall→diagonal) for a demo that doesn't need horizontal spreading?
