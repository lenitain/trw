# F2: Grid-based cellular automata for water/fluid simulation

## Findings

### [1] Sandspiel's cellular automata architecture uses a dense 2D grid where each particle state is a 32-bit struct (species + 2 state registers + clock), with positions encoded as array indices rather than explicit coordinates.
- quote: "The state for a single particle is represented as a 32 bit struct... species is a custom enum type which represents the varieties of particles as numbers... ra and rb are two 8 bit 'registers' for storing extra cell state... clock is just used to prevent a single particle from being simulated multiple times in a single tick"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [2] Water in Sandspiel is simulated with local neighbor-checking: it falls down first, then diagonally, then flows horizontally using a direction bias stored in the ra register, with "opinion spreading" to communicate flow direction to adjacent water particles.
- quote: "let below = api.get(0, 1); if below.species == Species::Empty || below.species == Species::Oil { api.set(0, 0, below); api.set(0, 1, Cell { ra, ..cell }); }... if dx0.species == Species::Empty && dxd.species == Species::Empty { api.set(0, 0, dxd); api.set(2 * dx, 0, Cell { rb: 6, ..cell }); // spread opinion if nbr.species == Species::Water { if nbr.ra % 2 != cell.ra % 2 { api.set(dx, dy, Cell { ra: cell.ra, ..cell }) } }"
- url: https://raw.githubusercontent.com/MaxBittker/sandspiel/master/crate/src/species.rs
- source_type: primary
- published: 2018 (last commit)
- confidence: high

### [3] Each particle's update function runs thousands of times per frame and is defined as a single method that reads/writes to neighbors via relative offsets (api.get(dx, dy)), abstracting away position, boundary handling, and neighborhood constraints.
- quote: "Designing and tuning these update functions was a lot of fun... these update functions, which hold so much of the gameplay logic, are run thousands of time per frame! This means that they're simultaneously critical to the feel of the game, and are some of the hottest lines of code in the project."
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [4] Sandspiel achieved 60fps on a 300x300 grid using Rust compiled to WASM, with the simulation running on the CPU and rendering on the GPU. The author notes a performance mistake of increasing resolution from 250x250 to 300x300 which broke 60fps on many devices.
- quote: "A big mistake I made was to immediately take this extra performance budget and 'spend it' to increase my canvas size from 250x250 to 300x300, because now I could still get 60 fps on the 300x300 canvas. This was a blunder because there are a ton of devices which can't run sandspiel at 60fps"
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [5] The computational complexity of a falling sand cellular automata is O(N) per frame where N is total grid cells, since each cell is processed exactly once per tick via left-to-right, top-to-bottom scan. A "clock" field prevents cells from being updated multiple times when they move ahead of the scan line.
- quote: "clock is just used to prevent a single particle from being simulated multiple times in a single tick if it moves in the same direction as the update scans. Because we execute cell update functions one at a time from left to right and top to bottom, if a particle something is moving down, it will keep bumping itself ahead of the 'scan line' and could move many spaces in a single frame."
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [6] Sandspiel separates particle simulation (CPU cellular automata) from fluid dynamics (GPU Navier-Stokes), with the fluid sim providing wind/pressure effects that interact with particles. The Navier-Stokes approach is based on GPU Gems Ch.38 "stable fluids" method.
- quote: "Sandspiel's fluid simulation usually really stands out to people who play with it, which makes me feel a little bit guilty, because it's largely ripped from Pavel Dobryakov's WebGL Navier-Stokes implementation... This chapter describes a method for fast, stable fluid simulation that runs entirely on the GPU... The techniques we describe are based on the 'stable fluids' method of Stam 1999."
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [7] For a falling sand game, water flow rate is controlled by the horizontal spread mechanism: water moves 1-2 cells horizontally per tick, with a random direction bias (ra register) and a "confidence" counter (rb) that affects bumpability. This creates natural-looking pooling behavior.
- quote: "let left = cell.ra % 2 == 0; dx = if left { 1 } else { -1 }; let dx0 = api.get(dx, 0); let dxd = api.get(dx * 2, 0); if dx0.species == Species::Empty && dxd.species == Species::Empty { // scoot double api.set(0, 0, dxd); api.set(2 * dx, 0, Cell { rb: 6, ..cell }); } else if dx0.species == Species::Empty || dx0.species == Species::Oil { api.set(0, 0, dx0); api.set(dx, 0, Cell { rb: 3, ..cell }); }"
- url: https://raw.githubusercontent.com/MaxBittker/sandspiel/master/crate/src/species.rs
- source_type: primary
- published: 2018 (last commit)
- confidence: high

### [8] The Sandspiel architecture uses a clean API boundary between engine and element logic: each element's update function receives a SandApi struct that provides get/set with relative coordinates, hiding absolute position and grid boundary concerns from element code.
- quote: "SandApi is a struct provided to the function which holds the location of the particle without directly exposing their values. It exposes some important functions, like get and set, which accept relative coordinates and let you read and write to your neighboring cells. For instance, api.get(0, 1).species tells you the species of the particle below you."
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [9] Sandspiel's game state is stored in a format that doubles as a valid image texture (4 bytes per cell = RGBA), enabling zero-copy transfer from WASM memory to WebGL for rendering, with rendering blocking the CPU for less than 1 millisecond.
- quote: "Because our game state data is arranged in such a way that it happens to be a valid image texture, we can ship the whole grid over to the GPU with minimal copying and allocation!... the rendering code blocks the CPU for less than 1 millisecond, critical for meeting the strict 16ms budget needed to achieve 60FPS."
- url: https://maxbittker.com/making-sandspiel
- source_type: primary
- published: 2019-04-30
- confidence: high

### [10] Sand particles in Sandspiel also displace lighter fluids (water, gas, oil, acid) when falling, implementing basic density-based layering without explicit pressure simulation.
- quote: "if nbr.species == Species::Water || nbr.species == Species::Gas || nbr.species == Species::Oil || nbr.species == Species::Acid { api.set(0, 0, nbr); api.set(0, 1, cell); }"
- url: https://raw.githubusercontent.com/MaxBittker/sandspiel/master/crate/src/species.rs
- source_type: primary
- published: 2018 (last commit)
- confidence: high
